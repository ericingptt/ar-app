# 佐臻 AR 眼鏡手勢操作規格

本文件描述「用佐臻 J-Reality AR 眼鏡的 ToF 手勢操作網頁內容（CIBAR）」這套系統目前的
完整設計、實際限制與軟硬體契約。目的是讓不在這個開發脈絡裡的人，也能據此討論整合方式。

- 對象 repo：`ericingptt/ar-app`（Android 外殼）、`ericingptt/CIBAR`（網頁內容）
- 對應版本：`ar-app` branch `claude/jorjin-tof-gesture-recognition-275iub`（v1.0.1+46 起）
- 文中標示「**已實測**」＝已在實機或自動化測試驗證；「**需實機驗證**」＝尚未驗證

---

## 1. 一句話說明

Android 手機透過 USB 連接佐臻眼鏡，我們自己的 App 直接讀取眼鏡 ToF 感測器的深度資料，
在手機端算出手勢，再把手勢轉成網頁上的「選哪一個按鈕」，操作載入在 WebView 裡的 CIBAR。

**全程不需要、也不會啟動佐臻原廠的 `J-Reality-Gesture` App。**

---

## 2. 系統組成

```
佐臻眼鏡 ToF 模組
   │  USB CDC-ACM（虛擬序列埠，與 RGB 相機是不同的 USB 裝置）
   ▼
JJSDK v1.3.3（原廠 AAR）
   │  TofIncomingFrameListener → 每幀 8×8 深度網格
   ▼
TofGestureRecognizer（我們寫的，Java）
   │  手勢：UP / DOWN / LEFT / RIGHT / PUSH / PULL / HALT / PRESENCE / SELECT
   ▼
CibarActivity（WebView 外殼）
   │  evaluateJavascript：window.__jjsdk.onGesture(code, name)
   ▼
gesture-bridge.js（注入 CIBAR 頁面）
   │  決定「這個手勢要按哪一顆按鈕」
   ▼
CIBAR（React 網頁，完全不需要修改）
```

**關鍵設計決策：選取邏輯放在注入的腳本裡，不放在 CIBAR 原始碼裡。**
好處是兩邊可以各自演進、CIBAR 不必為了手勢改架構；代價是腳本必須靠推斷理解頁面結構
（第 5 節），而推斷的正確率可以用第 6 節的標註契約提升到 100%。

---

## 3. 硬體事實與限制（這些決定了所有設計）

### 3.1 感測器只有 64 個測距點

ToF 模組每幀回傳 **8×8 = 64 個 zone**，每個 zone 只有一個距離數字（mm）與訊號強度。
**它沒有影像、沒有形狀資訊**，不是深度相機。

每個 zone 對應約 5.6° 視角，換算成實際空間大小：

| 距離 | 一個 zone 的寬度 | 手指(≈1.8cm)佔 | 手掌(≈9cm)佔 |
|---|---|---|---|
| 15 cm | 1.5 cm | 1.2 格 | 6.1 格 |
| 25 cm | 2.5 cm | 0.7 格 | 3.7 格 |
| 35 cm | 3.4 cm | 0.5 格 | 2.7 格 |
| 45 cm | 4.4 cm | 0.4 格 | 2.0 格 |

**結論：只能做手掌等級的手勢，不可能做手指手勢。** 這不是實作問題——原廠 App 用的是
同一份 64 格資料，一樣只能做到手掌等級。要做手指級別需要深度相機或 RGB 影像辨識。

### 3.2 操作參數（目前設定，可調）

| 參數 | 值 | 說明 |
|---|---|---|
| 有效距離 | 20–450 mm | 超出範圍的 zone 視為沒東西 |
| 最少亮區 | 3 格 | 少於 3 格視為雜訊，不是手 |
| 方向判定門檻 | 中心點移動 ≥ 1.5 格 | 低於此不算方向性揮動 |
| 前後判定門檻 | 平均距離變化 ≥ 60 mm | PUSH / PULL 用 |
| 揮動時間上限 | 1600 ms | 更慢就不算揮動 |
| 停留選取時間 | 900 ms | 手不動滿這個時間就「按下」 |
| 停留容許漂移 | 1.1 格 / 55 mm | 超過就重新計時 |

### 3.3 韌體造成的兩條路徑

ToF 手勢有兩種來源，**目前實機用的是第二種**：

| 路徑 | 資料來源 | 韌體需求 | 現況 |
|---|---|---|---|
| A. 韌體手勢引擎 | 韌體算好的手勢位元（深度幀第 586–590 byte） | **需 ≥ v1.2.2** | 測試機韌體為 **1.1.2**，此路徑永遠不會觸發 |
| B. 主機端運算 | 原始 8×8 深度幀，我們自己算 | 任何韌體 | **目前使用中，已實測可用** |

原廠 Gesture App 走的也是路徑 B（其 native library 只匯出
`Java_com_jorjin_gesture_services_tof_ParseRunnable_calculateGesture`，自己從深度網格算）。

**兩條路徑同時保留**，畫面會標示手勢來源（「韌體」或「深度幀」）。若日後韌體升級到 1.2.2，
同樣的手勢會改從路徑 A 進來，行為不變。

> 補充：韌體升級檔就在原廠 APK 內（`res/raw/tof_v122_jg7hc`，STM32 DfuSe 格式，版本欄
> `0x0122`）。但該檔的 DFU 標頭指向 `VID 0x350E / PID 0x3723`，而測試機的 ToF 目前列舉為
> `0x0483 / 0x5740`。**刷錯韌體會使模組失效，升級前需向佐臻確認相容性。**

## 4. 手勢辨識（手機端）

### 4.1 演算法

每一幀：
1. 取出距離落在 20–450 mm 的 zone，視為「手」。
2. 少於 3 格 → 視為沒有手。
3. 計算這些 zone 的**中心點**（row, col）與**平均距離**。

狀態機：
- 手出現 → 記錄起點，發出 `PRESENCE`，開始計算停留。
- 手移動超過容許漂移 → 停留計時重來（**所以揮動永遠不會誤觸發選取**）。
- 手不動滿 900 ms → 發出 `SELECT`（一次停留只發一次）。
- 手離開 → 比較起點與終點，取位移最大的軸決定手勢。

方向判定（取三軸中超過門檻且最大者）：
- 水平位移最大 → `LEFT` / `RIGHT`
- 垂直位移最大 → `UP` / `DOWN`
- 距離變化最大 → `PUSH`（靠近）/ `PULL`（拉遠）
- 都沒超過門檻但停留夠久 → `HALT`

### 4.2 手勢清單與可靠度

| 手勢 | 動作 | 可靠度 |
|---|---|---|
| `LEFT` / `RIGHT` | 手掌左右揮 | **高**（已實測） |
| `UP` / `DOWN` | 手掌上下揮 | **高**（已實測，兩軸解析度相同） |
| `SELECT` | 手掌停住 ~1 秒 | **高**（只需「有手且不動」） |
| `PRESENCE` | 手進入範圍 | 高 |
| `PUSH` / `PULL` | 手掌前後移動 | **低——不建議作為主要操作** |
| `HALT` | 停住但未達選取條件 | 中 |

**為什麼 PUSH / PULL 不可靠**：兩者都靠「平均距離變化」判斷，而距離是這顆感測器最吵的一軸；
手很難不偏移地直直推向感測器，實際上常常被判成左右或上下。因此**選取改用「停住不動」**，
PUSH 僅保留為備用。

### 4.3 方向可能相反

模組的安裝方向無法從軟體得知。App 畫面上提供「左右對調」「上下對調」兩個開關，
設定會保存。**需實機確認**是否需要對調。

## 5. 網頁端選取規則（`gesture-bridge.js`）

腳本在頁面載入完成後注入，**CIBAR 完全不需要修改**。

### 5.1 什麼算「可互動元素」

```
[data-gesture-focusable]、a[href]、button:not([disabled])、[role="button"]、
input（非 hidden/disabled）、select、textarea、[tabindex]:not([tabindex="-1"])
```
且必須實際可見（有 client rect、非 `display:none`／`visibility:hidden`／`aria-hidden`）。

### 5.2 兩種操作模式，自動切換

#### 模式 A：直接選擇（揮哪邊就選哪個）— 主要模式

腳本找出畫面上的「選項組」，把每個選項綁定一個方向，**揮動即選擇，不需要確認動作**。

**選項組怎麼挑**（這裡踩過兩個坑，規則是修正後的）：
1. 把可互動元素依「共同父節點」分組。
2. 只考慮成員數 1–4 的組（超過 4 個沒有足夠方向可分配）。
3. 取**合計面積最大**的那一組。
4. **但如果畫面上存在任何更大的一組控制項，就不啟用直接選擇**，退回模式 B。

第 4 條同時解決兩個問題：
- 底部導覽列也是 2–4 個控制項，若只看數量會把揮動綁到導覽列而不是題目。
- 選項超過 4 個的畫面上，導覽列會變成唯一「數量合格」的組，反而預設搶走揮動。

（這兩個都是實際被自動化測試抓到的 bug，不是假設。）

**方向怎麼分配**：依選項在畫面上的**實際座標**，先判斷這組是橫向還是直向排列，
兩端取該排列軸，中間的取垂直軸。

| 選項數 | 橫排 | 直排 |
|---|---|---|
| 1 | 右 | 右 |
| 2 | 左 / 右 | 上 / 下 |
| 3 | 左 / **上** / 右 | 上 / **左** / 下 |
| 4 | 左 / **上** / **下** / 右 | 上 / **左** / **右** / 下 |

**畫面提示**：每個選項上會浮出一個箭頭徽章（← → ↑ ↓），使用者不需要記憶對應關係。

#### 模式 B：移動焦點 + 停留選取 — 後備模式

超過 4 個選項、或不成組的畫面（長列表、feed）自動使用：

| 手勢 | 動作 |
|---|---|
| 四方向揮動 | 把焦點移到**該方向上實際存在的**元素；該方向沒有元素時，移到閱讀順序的前／後一個 |
| **停住不動 ~1 秒** | **按下目前焦點的元素**（倒數期間該元素上有橫條填滿） |
| `PULL` | 回上一頁 |
| `HALT` | 重新掃描頁面元素 |

方向移動是**空間導航**：從目前元素中心往該方向找最近的元素，並對「垂直於揮動方向的偏移」
加權，因此按鈕格狀排列時「往右揮」會選到右邊那顆，而不是 HTML 裡的下一個節點。
焦點移動時會自動捲進畫面，所以不需要獨立的捲動手勢。

### 5.3 頁面變動的處理

CIBAR 是 React，DOM 會頻繁重繪。腳本以 `MutationObserver`（合併成每 150 ms 一次）
與 `hashchange` 觸發重新掃描，並盡量讓焦點停在同一個元素上。

### 5.4 觸控永遠可用

手勢辨識不是唯一入口。展場的公開展示不應該只靠手勢。

## 6. CIBAR 可以做的事（軟硬體契約）

以下都是**可選**的——不做也能運作，做了會更準。這是整合討論的重點。

### 6.1 目前已支援的標註

| 屬性 | 用途 |
|---|---|
| `data-gesture-dir="left\|right\|up\|down"` | **指定某個選項綁定哪個方向**，覆寫腳本的自動推斷 |
| `data-gesture-focusable` | 讓非標準元素（例如 `<div>` 卡片）也能被選取 |

### 6.2 建議的內容設計原則

1. **每個決策畫面盡量控制在 4 個選項以內。** 超過 4 個就會退回「移動焦點 + 停留 1 秒」，
   操作速度大約慢 3–4 倍。目前 CIBAR 統計：3 個選項 42 處、4 個選項 30 處、2 個選項 6 處、
   1 個選項 2 處、7 個選項 1 處——**只有 1 處需要調整**。
2. **選項按鈕要明顯大於導覽列／裝飾性控制項。** 選項組是用面積挑的。CIBAR 現況
   （`.btns` 橫跨整個手機框、導覽項目很小）已經天然符合。
3. **把「安全」的選項固定放在同一側**（例如永遠把「拒絕／檢舉」放右邊），
   使用者揮錯的機率會大幅下降。
4. **同一個決策的選項要放在同一個父容器裡。** 腳本靠共同父節點分組；
   若選項散落在不同容器，會被當成不同組。
5. **不要用 `disabled` 以外的方式讓按鈕失效**（例如只用 CSS 蓋住），
   那樣腳本仍會把它算成可選項。

### 6.3 建議新增的標註（尚未實作，可討論）

若希望完全不依賴推斷，建議加上：

| 屬性 | 用途 |
|---|---|
| `data-gesture-group` | 明確標出「這個容器就是本畫面的選項組」，腳本不再猜 |
| `data-gesture-ignore` | 明確排除（導覽列、裝飾性連結） |
| `data-gesture-hint="文字"` | 提供給徽章／HUD 顯示的簡短說明 |

**我的建議：先加 `data-gesture-group` 與 `data-gesture-ignore` 這兩個。** 它們成本極低
（各一個屬性），但能把「選項組挑錯」這個最大風險降到零。方向仍可交給腳本從座標推斷，
只有需要特別指定時才用 `data-gesture-dir`。

## 7. 現況與尚未驗證的部分

### 已實測可用
- 眼鏡 RGB 相機（640×480，影像幀持續累加）
- ToF USB 偵測、授權、連線、深度幀串流
- `LEFT` / `RIGHT` / `UP` / `DOWN` 四方向手勢辨識

### 已通過自動化測試（jsdom，非實機）
- 七種版面的方向綁定（橫排／直排 × 1～4 選項、7 選項退回模式 B）
- 揮動確實觸發對應按鈕的 click
- 導覽列不會搶走揮動
- `data-gesture-dir` 覆寫

### 需實機驗證
- 手勢方向是否需要左右／上下對調
- 停留 900 ms 的長度是否合適（太久使用者會不耐，太短會誤觸）
- 選取容許漂移（1.1 格 / 55 mm）對一般使用者是否太嚴格
- 在真實 CIBAR 頁面上，選項組是否都被正確辨識
- 連續操作多個畫面時的穩定度與疲勞度

### 已知限制
- **只能手掌，不能手指**（第 3.1 節）
- 強烈日光、紅外線光源會干擾 ToF
- 一次只能追蹤一隻手，沒有雙手手勢
- 沒有「取消」手勢；直接選擇模式下揮出去就會執行，目前只能靠 `PULL`（回上一頁）補救

## 9. 給整合討論的關鍵問題

1. CIBAR 是否願意加上 `data-gesture-group` / `data-gesture-ignore` 兩個標註？
   （成本極低，可消除最大的推斷風險）
2. 那 1 處 7 個選項的畫面要拆成兩層，還是接受它退回「停留選取」模式？
3. 是否需要「取消／回上一步」的專用手勢？目前只有 `PULL`，而 `PULL` 本身不可靠。
4. 展場情境下，是否需要「閒置自動重置到首頁」？（目前沒有）
5. ToF 韌體要不要升級到 1.2.2？升級後多一條硬體手勢路徑，但有相容性風險（第 3.3 節）。
